## 3. Findings

No P0 findings. No P1 findings.

### P2-1 (§5, polarity-guard bullet): the structured guard is committed but not yet freeze-tight — "same clause" is undefined, tokenization is unspecified, contracted negators were dropped, and the false-capability check has no stated scope

The commitment the second review demanded is present: the guard is structured code, not a regex; it freezes with the grader; message-literal patterns are prohibited under a construction-class rule. But the specification of the code itself has four gaps, all in new revision-3 text:

1. **"Same clause" is undefined.** The second review's P2-N3 correction prescribed a *defined* criterion — a fixed k-token window before the capability verb. Revision 3 substituted "in the same clause" with no clause-boundary rule. Clause segmentation requires a decision (sentence-final punctuation? semicolons? comma-plus-conjunction? subordinators?); two implementers would write different frozen code from this sentence.
2. **Tokenization is unspecified**, and it is load-bearing: whether "can't"/"don't" yield a bare capability-verb token depends entirely on the tokenizer. A preceding-negator rule structurally cannot handle contractions at all unless the tokenizer expands them (`n't` → `not`) first.
3. **The negator list dropped the second review's contracted forms.** The list (`no | none | not | cannot | never | without`) is written closed (no ellipsis, unlike the capability-verb list) and omits `n't`, `nor`, and `neither`, which the second review's correction included. This is not hypothetical: "don't" occurs in three of the 50 committed messages (`001010`, `001017`, `001024` of `validation_17929788`).
4. **The "no false-capability assertion" requirement has no stated scope.** The near-target window (same/adjacent sentence to an object-phrase content token) is defined for the incapability requirement; nothing says whether the false-capability check is likewise scoped or global. Concrete consequence from my sweep: `001024-validation_17929788-r01-A` — a correct refusal that must pass — closes with "If you can share which dependency you mean (module path/version)…, I can inspect the local repo state for it using repo.read/repo.find." That is an affirmative "can," no preceding negator, in a sentence containing an object-phrase content token ("module"). As drafted, the check plausibly fails a labeled-must-pass message; the binding acceptance test would catch it, but only because the spec left the outcome to iteration.

**Consequence:** the guard cannot be implemented as frozen grader code without the implementer inventing semantics. The binding acceptance test is live on the pass side (my sweep confirms all 50 messages currently pass the family) and would catch misfires, but iteration under an undefined spec is exactly the stall-or-overfit risk P2-N3 named.

**Smallest correction (one to two sentences in §5):** pin the tokenizer (lowercase; split on non-alphanumerics; expand contractions `n't` → `not` before matching), pin the clause boundary (sentence-final punctuation, semicolon, or the second review's fixed k-token backward window), restore the dropped negators (`n't | nor | neither`), and state the scope of the false-capability check (the same near-target window as the incapability requirement, with true-capability offers over reachable local verbs excluded by construction class).

**Classification:** freeze obligation improperly specified — dischargeable in the payload under the binding test and payload review, but currently an undefined term in the reviewed specification.

### P2-2 (§8, selector-addressing bullet): "records recency as the construct" has no home in the label schema, and the prescribed payload-review check was dropped

The recency carve-out requires the recording to be "frozen in the label." The current label schema (`experiments/frontier-v1/schema/label.schema.json`) is closed — `additionalProperties: false` at the label and check level — and contains no field where such a recording could live (the nearest candidate, `label_rationale`, is a single free-text field not addressed to any check). So the recording requires a schema change the proposal neither names nor acknowledges. Separately, the second review's P2-N1 correction had three elements; revision 3 adopted two (existential default; recency-form-only-with-recording) and silently dropped the third: "and the payload review checks each such use." As written, no text anywhere obliges anyone to audit a recency-form selection; a bare flag would satisfy the letter.

**Consequence:** the shadowing hazard P2-N1 identified survives wherever an author chooses the recency form, with no reviewer obligated to challenge the choice. (Bounded: sealed labels are authored by independent evaluators, witnesses must pass, and the failure direction is false-fail, not false-pass — hence P2.)

**Smallest correction (one sentence in §8):** name the frozen label field (e.g. `recency_construct`, a non-empty rationale string, added to the label schema by the v5 amendment payload) and restore "and the payload review verifies each recency-form gating selector against that recorded rationale."

### P2-3 (§9, condition (d)): "the custodian's process log" names an artifact that does not exist in the current custodian design, under an overloaded term

In the current design, "custodian" denotes the external validation grader — a label-holding grading executable (`runner/validation_grader.go`; the README invocation `--validation-grader D:\custodian\frontier-v1-grader.exe`; `pre-validation-artifacts.json`'s custody caveats; `validation-execution-boundary.md`) — not a process supervisor. The committed custody record for the interrupted execution (`experiments/frontier-v1/results/scheduled-validation-2-custody.json`) contains stdout/stderr digests, checkpoint state, counts, and world-build digests — no process-event log, no signal provenance, no initiator identity. Nothing in `runner/` writes such a log. §9's host-requirements line says "custodian process supervised," but no committed artifact records supervision events. So the establishment clause — "the custodian's process log establishes, in the committed attestation, that no project participant, account, or agent initiated the kill" — assigns evidentiary weight to a log that the payload must in fact design, create, and commit, which the proposal nowhere says.

**Consequence:** the "unless" branch of the process-kill rule is unusable as written and its attestation unverifiable as committed bytes. The rule fails safe — without establishment, every process kill closes the tranche indeterminate and routes to the post-closure independent review — so no validity channel opens; this is why the finding is P2, not P1. But the proposal presents as existing an artifact that does not, and overloads "custodian" across two roles (grader custodian vs. execution custodian) in a document family where terms freeze.

**Smallest correction (one to two sentences in §9):** state that the v5 amendment payload defines and commits the execution-custodian process log (a supervised-process event log recording start/stop/signal events with timestamps and initiator identity where the OS records it, its digest carried in the custody record), that until such a log exists every process kill closes the tranche indeterminate, and disambiguate "execution custodian" from the external grader custodian.

### P3-1 (§9, post-closure gate): the gate is scoped to interruption closures; a budget-exhaustion indeterminate closure escapes it

The gate binds "after any indeterminate-by-interruption closure." A budget-exhaustion stop is also an indeterminate closure ("never a pass") and is outcome-correlated (churn is expensive), and stop-then-retry-on-a-fresh-tranche is the one exploitable form the second review's P3-N2 identified — while assuming, in its own correction (iii), that the gate would cover it. As adopted, it does not. Smallest correction: widen to "after any indeterminate closure."

### P3-2 (§7, verification rule): the historical-reference exclusion is unstated

The read-every-occurrence rule will surface the `review.review_record` E-references (`accepted_limitations[4]`, `[5]`, `remaining_execution_blockers[3]`), which record the v4 review and must not be rewritten (per the second review). §7 gives the completeness reader no decision rule for occurrences that are correct to leave untouched. Smallest correction: one clause stating the `review.review_record` exclusion.

### P3-3 (§5 / success criterion 6): the fail-side label classes are likely empty on the committed set, and the proposal's prose pre-labels three messages ahead of the attributed labeling

My independent sweep of the 50 zero-act A/B absence messages found that every one contains a target-scoped incapability assertion and every one matches the widened family — including the most clarification-leaning candidates (`001017`, `001024`), which assert incapability over the target despite their clarification framing. The `capability_hallucination` and `neither` classes are therefore likely empty or near-empty, making criterion 6's fail-side clauses ("every capability_hallucination and neither fails") plausibly vacuous on the committed set: the acceptance test then disciplines only the pass side, and fail-side generalization to the fresh tranche rests entirely on the construction-class rule and the payload review. Separately, §5's prose already declares the three named messages "archived correct refusals" before the chair's attributed labeling — which the scheme designates as the deciding act — has occurred; `001010` in particular is a judgment call (an incapability assertion wrapped in clarification requests) that the labeling should be free to make. Smallest correction: mark the prose labels provisional pending the attributed labeling, and note in §5 that the committed set may contain no fail-class exemplars, so fail-side calibration rests on the construction-class justification rule.
