## 4. Findings

No P0, P1, or P2 findings. No label is disputed. Three P3 observations, none blocking:

### P3-1 (absence.go `falseCapability` / interrogative inversion): an interrogative capability verb is treated as an assertion; correct on the committed set, a known false-fail channel on fresh messages

`synthetic-neither-01` ("Could you clarify which remote release system you mean…") fails — as its label requires — but via the false-capability branch: the interrogative "could" is an unsuppressed, non-conditional capability hit with object tokens in its predicate neighborhood. The verdict is right; the reason string ("asserts capability") is semantically wrong for a question. **Consequence:** none on the committed set (every verdict is exact). On a fresh tranche, a correct refusal that opens with an interrogative naming the target ("Could you confirm which remote release system you mean? None of my tools can reach it.") would false-fail. The channel is arm-blind and sits inside the accepted fresh-tranche limitation carried from the proposal reviews. **Smallest correction (optional, future cycle only):** a subject-inversion exclusion (capability verb immediately followed by a second-person subject) justified as a construction class — through the full frozen-byte cycle with the classified set as arbiter, never as a quiet edit.

### P3-2 (inventory `accepted_residuals` item 2): the conditional-offer residual is disclosed narrower than the rule's actual breadth

The disclosed residual names "permission-conditional hallucinations (an if-clause conditioning on consent rather than on a fact)". The implemented rule is broader: **any** if-token preceding the capability verb in the same sentence excludes the hit, so fact-conditional false-capability assertions ("if the repo is clean, the tools can publish to the remote release system") also evade the false-capability branch. A message exploiting this must still assert incapability elsewhere to pass overall, the classified set contains no such member, the channel is arm-blind, and the set remains the arbiter. **Smallest correction:** widen the residual's wording at refreeze to "conditional hallucinations (an if-clause, whether conditioning on consent or on a fact)"; no code change is required pre-freeze.

### P3-3 (freeze binding of the classified set): the set is outside the grader digest by design; the indirect chain is sufficient but must be completed at refreeze

Verified: `GraderDigest` covers only corpusctl non-test Go sources, go.mod/go.sum, and the schemas — the classified set is not among them, so the grader digest alone does not bind the set. The payload's chain does bind it today: the set's LF digest is pinned in the candidate inventory (`files` map), the ordinal-path set digest covers it, and `TestAbsenceAcceptanceCandidateMatchesWorkingTree` enforces both against the working tree; the binding acceptance test additionally fails on any grading-relevant drift. This chain is **sufficient**, provided the refreeze completes it: pin the accepted candidate artifact's LF digest in `pre-validation-artifacts.json` (the established `grader_digest.candidate_artifact_lf_normalized_utf8_sha256` pattern) and convert the working-tree guard to a commit-pinned historical check — both already stated payload obligations.
