# Task 0.6 independent Phase 0 review prompt

## Assignment

Review the Phoenix Phase 0 research contract at the candidate commit. This is a gate review, not an outcome run. Use three reviewers independent of the work they assess, followed by an accountable project-chair decision:

1. an evaluation reviewer for corpus validity, leakage controls, labels, and comparison design;
2. an implementation reviewer for surface feasibility, envelope schemas, and the O(1) harness;
3. a human-factors reviewer for frontier and refusal legibility;
4. a project chair who records the combined verdict and unresolved blockers.

One person may not approve their own implementation or corpus work. Record reviewer roles, dates, candidate commit, and any relevant independence limitation.

## Candidate prerequisites

The implementation and human-factors reviews may start against the current commit while the corpus evaluator works. Do not issue the final evaluation or project-chair verdict until the independent evaluator has submitted the package and report required by `docs/reviews/2026-08-18-sealed-corpus-evaluator-handoff.md`. Review that package before it is applied to the implementation workspace. Full validation and held-out labels remain with the external custodian and are shown only to the evaluation reviewer through a private channel.

The candidate must still have:

- no validation or held-out trial records or outcomes;
- `protocol.json` frozen and independently accepted;
- Task 0.2 evidence independently accepted;
- all `may_open_*` gates false.

## Evaluation review

Inspect Task 0.4, the frozen protocol, corpus schemas and tools, authoring tranche, proposed public sealed-corpus patch, external full labels, independence declarations, and adjudication records.

Return findings and a requirement matrix covering:

- exactly 120 cases, 24 families, and five distinct case variants per family in each sealed tranche;
- exact class totals and family allocation from the protocol;
- family and template separation across all three tranches;
- opaque inputs with no answer, class, grader, or path leakage;
- one complete private label and matching digest per case;
- deterministic grading where possible and blinded, retained adjudication where it is not;
- current grader digest, schema validity, manifest reproducibility, and denominator accuracy;
- no implementation or prospective outcome influence on case creation or labels;
- Arms A through E, comparisons, budgets, missing-data rules, kill rules, and claim scope remain internally consistent.

The evaluation reviewer may report label defects by case ID and finding without copying expected outcomes into the repository.

## Implementation review

Inspect Tasks 0.1 through 0.3, `spec/`, `experiments/surface-spike/`, the accepted Task 0.2 evidence, and the corpus/world schemas. Run at least:

```powershell
Set-Location experiments/surface-spike
go test ./...
go vet ./...
go run ./cmd/validate-spec --repo-root ../..
go run ./cmd/measure-schema --sizes 10,100,1000

Set-Location ../frontier-v1/corpusctl
go test ./...
go vet ./...
go run ./cmd/corpusctl validate --repo-root ../../.. --tranche authoring --world-source experiments/frontier-v1/worlds/authoring.dev_repo.json
```

Confirm the single standing tool, typed `act` call, session-scoped handles, absence behavior, status-dependent envelopes, bound frontier calls, structured refusals, schema unknown-field rejection, world validation, O(1) measurements, pinned runtime evidence, and documented failure modes. Separate Phase 0 feasibility from Phase 1 production work that the plan intentionally has not started.

## Human-factors review

Use `docs/reviews/2026-08-18-task-0.6-human-factors-pack.md`, the result examples, surface-spike rendering, and any independently captured authoring-only transcript. Decide whether a reader can reconstruct why each next action followed from the preceding frontier or refusal.

Return the required verdict and checklist from that pack. If the lack of a retained full spike transcript prevents acceptance, state the exact authoring-only evidence needed. Do not request or inspect a sealed-tranche run.

## Project-chair decision

The project chair records `ACCEPT`, `REVISE`, or `REJECT` in a candidate `docs/decisions/0005-phase-0-review.md`. The record must include:

- the candidate commit and LF-normalized UTF-8 SHA-256 digests of every reviewed decision, protocol, result file, sealed manifest, and public evaluator report;
- reviewer roles, dates, verdicts, findings, accepted limitations, and independence declarations;
- corpus counts and confirmation that private labels remain external;
- every unresolved blocker with an owner and the artifact needed to clear it;
- an explicit statement that no sealed outcome was opened;
- the exact next action authorized by the verdict.

`ACCEPT` requires all three reviews to accept, no unresolved priority 1 or priority 2 finding, complete independent validation and held_out candidates, and accepted corpus and go/no-go rules. An accepted Phase 0 contract authorizes importing the reviewed public sealed-corpus patch and beginning Phase 1 implementation. It does not authorize opening validation or held_out: first freeze the runtime invocation, system prompt, Arm A schemas, Arm B document, world build, runner, schedule, grader, analysis implementation, and report template by digest as required by `protocol.json`.

For `REVISE`, keep Phase 0 and every outcome gate closed and name the smallest next artifact that can resolve each finding. For `REJECT`, state which premise or contract failed and what work, if any, may continue.
